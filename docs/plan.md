# План

> ЧЕРНЕТКА v2. Джерела: 6 матеріалів (Session 1–6) і 2 протоколи мітингу. Є ще невизначеності (див. «Відкриті питання»).

## Поточний етап

Практичний курс «Spec Driven Development with AI»: як працювати з вимогами за допомогою AI. Складаємо план на 4 дні по 4 години (16 год).

## Узгоджені рамки (з мітингів)

| Аспект | Рішення |
|---|---|
| Аудиторія | Зовнішні учасники, серед них нетехнічні та початківці |
| Формат | Воркшоп: ведучі показують частину, учасники виконують інший приклад під керівництвом |
| Обсяг | 4 зустрічі по 4 години |
| Теорія | Мінімальна: принципи роботи з вимогами та їхня якість |
| Матеріали | Покрокові інструкції до кожного заняття + презентації + записи занять |
| Платформа | Moodle (PDF, документи, промпти, інструкції) |
| Самостійність | Той, хто пропустив заняття, проходить його за інструкцією та записом |
| Робота учасників | Шаблонний репозиторій → власна копія, локальна робота, надсилання посилань (бажано на PR) менторам |
| Технічний старт | Без Docker, мінімум інструментів, БД у пам'яті із seed-даних у коді; інструкції для Windows і macOS; Python/інші інструменти пояснюються просто |
| Обов'язково показати | Git і GitHub, налаштування Claude |
| Опція | Нова гілка для роботи з новим функціоналом |
| Потрібно письмово | Механізм перевірки та правила зарахування (критерії оцінювання) |

## Пропонований розподіл 6 сесій на 4 дні

Матеріали дають 6 сесій приблизно по 2 години (12 год змістовного контенту). Ще 4 год на 4 днях: вступ і налаштування середовища, розбір завдань, перевірка/зарахування.

| День | Блок (4 год) | Зміст | Джерело |
|---|---|---|---|
| 1 | Старт і контекст проєкту | Git/GitHub, шаблонний репозиторій, Claude/Cursor, AGENTS.md (CLAUDE.md), Markdown, Mermaid-діаграма; запуск застосунку | Session 1 + початок Session 2 |
| 2 | Від вимоги до коду | Трасування фічі UI→БД, правила для docs/, Humanizer, subagent; GitHub MCP, traceability, аналіз впливу, AC (Given/When/Then) | Session 2 + Session 3 |
| 3 | Гіпотези та прототипи | Sandbox-гілка, seed, PoC, diff простою мовою, чекліст валідації; прототип/handoff (Figma частково, див. питання) | Session 4 + Session 5 |
| 4 | Структуровані специфікації (SDD) | Spec Kit / OpenSpec / BMAD, 8 артефактів, ID (RULE/OUT/AC/Q), AI-вправи з guardrails, PoC/MVP-зріз; підсумкове завдання й критерії зарахування | Session 6 + підсумок |

Примітка: розподіл орієнтовний. Сесії 4–5 разом завеликі для одного дня, тож Figma-частину можна скоротити або зробити опційною.

## Кроки

1. Узгодити розподіл за днями (таблиця вище).
2. Дочекатися решти матеріалів (було 10 файлів, отримано 8).
3. Для кожного дня скласти деталізований план для викладача: хвилини, вправи, демо й самостійна частина, чекпоінти.
4. Письмово визначити критерії перевірки та зарахування (що здають, у якій формі, що вважається зарахованим).
5. Підготувати інструкції запуску для Windows і macOS без Docker, на спрощеному технічному стеку.
6. Визначити структуру курсу в Moodle (розділ на день: інструкція, презентація, запис, завдання).
7. Скласти `docs/spec.md` (вимоги до курсу) за джерелами.

## Спостереження за матеріалами

- Інструмент змінюється: Cursor (сесії 1–3), Claude Code у VS Code (4–5), нейтральний SDD (6). Для зовнішньої аудиторії варто обрати один основний інструмент. На мітингу згадано налаштування Claude.
- Наскрізні кейси різні (lf-client, Order Desk, пауза підписки). Для зв'язності бажано один кейс.
- Сесія 5 потребує Figma Make і Figma MCP, а це додатковий акаунт і налаштування для новачків.
- Сесія 3 вимагає PAT-токена GitHub, що потребує окремої інструкції та безпечної гігієни токенів.
- Сесія 6 посилається на файли воркшопу (`workshop/templates`, `workshop/exercises`, `workshop/ai-prompts.md`), яких серед отриманих немає.

## PoC-сценарії на lf-client (заміна Order Desk, чернетка)

| Гіпотеза | Що змінюється | Що спостерігаємо |

| Телефон у формі контактів обов'язковий | `validateContactData.ts` (гілка `if (phoneNumber)`), схема Zod у `ContactForm.tsx` | Чи правило лише в UI, чи й в API; розбіжність клієнт/сервер |

## Чернетка правил перевірки та зарахування

> ЧЕРНЕТКА для узгодження. Числа орієнтовні.

**Що здає учасник.** Для кожного з 4 днів одне посилання на pull request у власному репозиторії (створеному з шаблону). У PR: виконані завдання дня й короткий опис, що зроблено. Посилання надсилається ментору (канал уточнити, наприклад форма в Moodle).

**Завдання дня.** Кожен день має 1 обов'язкове завдання (мінімум) і 1 додаткове.

| День | Обов'язкове завдання (PR) | Додаткове |
|---|---|---|
| 1 | AGENTS.md проєкту + Mermaid-діаграма | Власні правила у `.cursor/rules` |
| 2 | Документ фічі з AC (Given/When/Then) і таблиця правил | Аналіз впливу, коментар до issue |
| 3 | Sandbox-PoC: diff + чекліст валідації | Прототип за макетом Figma |
| 4 | Структурована специфікація (8 артефактів, ID) + PoC/MVP-зріз | Edge cases та питання стейкхолдерам |

**Критерії оцінки одного завдання.**
1. Виконано всі пункти інструкції (так/ні).
2. Результат відповідає шаблону (структура, ID, формат AC).
3. Є власний аналіз, а не лише AI-вивід (позначено, що виправлено чи відхилено).
4. Немає вигаданих фактів і секретів у репозиторії (токени, .env).

**Поріг зарахування (пропозиція).**
- Зараховано: обов'язкові завдання щонайменше 3 з 4 днів, і серед них обов'язково день 4.
- Пропущені дні можна надолужити за інструкцією та записом упродовж, наприклад, 7 днів після завершення курсу.
- Не зараховано: менше 3 завдань або завдання без власного аналізу. Один раз можна доопрацювати за зауваженнями ментора.

**Хто перевіряє.** Ментор за чекліст-рубрикою (те саме 4 критерії). Відповідь до 3 робочих днів.

**Відкрито:** чи потрібні оцінки/бали, чи достатньо «зараховано/ні»; канал здачі; термін надолуження; чи видається сертифікат.
