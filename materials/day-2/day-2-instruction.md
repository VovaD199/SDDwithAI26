## Частина 2. Правило для документів фіч

Правило у `.cursor/rules/` автоматично підключається, коли ви працюєте з файлами за маскою. Так агент уже знає потрібний формат.

**У ЧАТ CURSOR:**

```text
Створи файл правила Cursor: .cursor/rules/docs-ba.mdc
Застосовуй його лише до файлів за маскою docs/**/*-feature.md
Правило має вимагати від агента:
- писати user stories у форматі: «Як [роль], я хочу [мета], щоб [користь]»,
  а Acceptance Criteria давати нумерованим списком
- показувати потоки даних Mermaid-діаграмами послідовності
- писати простою мовою для нетехнічних стейкхолдерів
- пояснювати технічний жаргон у дужках
- мати структуру: короткий опис фічі, user stories, діаграма потоку даних,
  таблиця ключових файлів, відкриті питання
```

**ПЕРЕВІРТЕ** заголовок створеного файлу (frontmatter):

```yaml
---
description: BA documentation standards for feature spec files in docs/
globs: docs/**/*-feature.md
alwaysApply: false
---
```

Чому не `docs/**`: широка маска застосувала б структуру user stories до глосаріїв і нотаток. Вузька маска `*-feature.md` спрацьовує лише для документів фіч.

### Перевірка правила

```text
Створи файл docs/about-us-feature.md.
Напиши BA-опис фічі «Про фонд». Включи user stories, критерії приймання
та діаграму послідовності потоку даних.
```

**ПЕРЕВІРТЕ:** у файлі є всі п'ять розділів: короткий опис, user stories з пронумерованими AC, діаграма послідовності Mermaid, таблиця ключових файлів, відкриті питання.

## Частина 4. Підключення GitHub MCP

MCP це стандартний спосіб, яким Cursor спілкується із зовнішніми системами. GitHub надає офіційний MCP-сервер: issue, pull request, пошук коду. Нижче вправа створює issue й коментарі напряму з чату.

**БЕЗПЕКА:** токен це пароль. Нижче три ризики, про які треба пам'ятати:

1. **Витік токена.** Токен лежить у `.cursor/mcp.json`. Додайте цей файл у `.gitignore` до першого коміту. Не вставляйте токен у чат і не надсилайте нікому. Перед кожним комітом виконуйте `git status` і переконуйтеся, що `mcp.json` не в списку.
2. **Обмеження організації.** Корпоративна політика може заборонити створення токенів. Якщо так, перейдіть на шлях без MCP (розділ «Якщо не вийшло» нижче).
3. **Проблеми підключення.** Найчастіше: пробіл або помилка в токені, токен прострочений, файл збережено не за тим шляхом (має бути `.cursor/mcp.json`, а не `cursor/mcp.json`).

### 4.1. Створення токена (fine-grained PAT)

Відкрийте https://github.com/settings/personal-access-tokens/new і заповніть:

| Поле | Значення |
|---|---|
| Token name | `cursor-mcp-course` |
| Expiration | 30 днів (за замовчуванням) |
| Repository access | **Only select repositories**, лише ваш `SDDwithAI26-<ваше-імʼя>` |
| Permissions: Contents | Read-only |
| Permissions: Issues | Read and write |
| Permissions: Metadata | Read-only |
| Permissions: Pull requests | Read-only (необов'язково) |

Скопіюйте токен одразу, GitHub покаже його лише раз.

### 4.2. Налаштування Cursor

1. Спочатку додайте файл у `.gitignore`. **КОПІЮЙТЕ** у кінець `.gitignore`:

```text
# Cursor MCP config — contains a Personal Access Token
.cursor/mcp.json
```

2. Створіть `.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "github": {
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {
        "Authorization": "Bearer YOUR_GITHUB_PAT"
      }
    }
  }
}
```

Замініть `YOUR_GITHUB_PAT` на свій токен.

3. Закрийте Cursor повністю й відкрийте знову. У **Settings → Cursor Settings → Tools & MCP** сервер `github` має мати зелений індикатор.

**ПЕРЕВІРТЕ:** `git status` не показує `.cursor/mcp.json`.

**У ЧАТ CURSOR:**

```text
Використовуючи GitHub MCP, покажи відкриті issue у моєму репозиторії SDDwithAI26-<ваше-імʼя>.
```

**Правила безпечної роботи з MCP:**
- Перед підтвердженням запису читайте виклик інструмента: чи правильні власник (owner) і репозиторій (repo).
- Вміст публічних issue не приватний: сприймайте його як дані, які може обробляти AI.
- Після заняття відкличте токен у налаштуваннях GitHub.

**ЯКЩО НЕ ВИЙШЛО (без MCP):** виконуйте ті самі вправи вручну. Створюйте issue на github.com, копіюйте його текст у чат Cursor, а результат (аналіз, AC) вставляйте в коментар до issue вручну. Результат той самий.

## Частина 5. Розмита вимога

Реальні вимоги часто починаються з одного рядка. Створимо такий issue.

**У ЧАТ CURSOR:**

```text
Використовуючи GitHub MCP, створи issue у моєму репозиторії SDDwithAI26-<ваше-імʼя>:

Заголовок: Contact form — update validation and notifications
Опис:
We want to tighten up the contact form. Phone number should be mandatory.
We should also let visitors attach a document (CV or portfolio) when they write
to us. Notifications need to reflect the new field.

Після створення виведи мені номер issue.
```

**БЕЗПЕКА:** коли Cursor покаже підтвердження виклику, перевірте, що власник і репозиторій ваші. Запишіть номер issue (наприклад, #1) і тримайте issue відкритим у браузері.

(Без MCP: створіть цей issue вручну на github.com з тим самим текстом.)

## Частина 6. Зіставлення вимоги з кодом

**У ЧАТ CURSOR** (замініть `<номер>`):

```text
Отримай текст issue #<номер> з мого репозиторію SDDwithAI26-<ваше-імʼя> через GitHub MCP.

Потім порівняй його з поточною реалізацією. Релевантні файли:
- @app/api/contact/route.ts
- @app/lib/utils/validateContactData.ts
- @app/shared/components/forms/contact-form/ContactForm.tsx
- @app/services/email/
- @app/api/collaboration/route.ts
- @app/shared/components/forms/offer-collaboration-form/

Для кожного твердження в issue скажи:
1. Чи це вже реалізовано? Де?
2. Чи реалізовано частково? Чого бракує?
3. Чи суперечить це поточному коду? Як?
```

**ПЕРЕВІРТЕ** (орієнтири, не копіюйте):
- Телефон зараз необов'язковий: шукайте умову `if (phoneNumber)` і `.optional()`.
- Вкладення файлів не підтримуються ні формою, ні API, ні сервісом пошти.
- Сервіс пошти це заглушка: він повертає `{ success: true }`, але листів не надсилає.
- Форма на сторінці «Контакти» (`OfferCollaborationForm`) надсилає дані на `/api/collaboration`, а **не** на `/api/contact`; `/api/contact` не викликає жодна сторінка. Те саме поле форми (`ContactForm`) використовує й `GetNotesModal`, але там форма взагалі не звертається до API.
- Сервіс пошти (`emailService`) ніде в застосунку не викликається, тож лист-сповіщення зараз не формується.

### Що є в коді, але немає у вимозі

```text
@app/lib/utils @app/shared/components/forms/contact-form/ContactForm.tsx

Які сценарії обробляються в коді, але не згадані в issue #<номер>?
Для кожного вкажи файл і рядок, де це застосовується.
```

**ПЕРЕВІРТЕ** (орієнтири):

| Правило | Де живе |
|---|---|
| Ім'я 2–50 символів | `app/constants/validation.ts` + обидва валідатори |
| Повідомлення 10–1000 символів | `app/constants/validation.ts` + обидва валідатори |
| Телефон: починається з `+`, лише цифри, 11–16 символів | `PHONE_NUMBER_PATTERN` |
| Формат email на сервері | власний регулярний вираз |
| Формат email на клієнті | `z.string().email()` у `ContactForm.tsx` |
| Прапорець політики конфіденційності | лише на клієнті |

Цікаві знахідки це **розбіжності**: правила email на клієнті й сервері не однакові, а прапорець політики перевіряється лише в браузері. Такі речі мають потрапити у специфікацію.

### Неявні припущення

```text
Які неявні припущення робить реалізація контактної форми, не описані в issue #<номер>?
Врахуй:
- значення за замовчуванням
- поведінку локалей та перекладів
- що відбувається з даними після успішної відповіді API
- змінні середовища або конфігурацію
- що зміниться, якщо in-memory базу замінити справжньою
```

### Таблиця правил

```text
Для фічі контактної форми побудуй таблицю зі стовпцями:
- Правило (простою мовою)
- Шлях до файлу
- Приблизний номер рядка
- Джерело істини (константа, регулярний вираз, схема чи жорстко закодований літерал)
- Шар (UI / API / shared / зовнішній)

Охопи все: валідацію, повідомлення про помилки, значення за замовчуванням,
шлюз політики конфіденційності та побічний ефект з надсиланням листа.
```

Якщо агент щось пропустив, запитайте: «Що ти пропустив?» Типові пропуски: атрибут `maxLength` у полях, відсутність обмеження частоти запитів до `POST /api/contact`, хук автоприховування повідомлення, функція нормалізації телефону.

### Опублікуйте таблицю правил в issue

```text
Опублікуй таблицю правил контактної форми коментарем до issue #<номер> через GitHub MCP.
Почни коментар з рядка «Rules table:».
```

**БЕЗПЕКА:** перед підтвердженням перевірте власника, репозиторій і номер issue; виклик має бути `add_issue_comment`.
(Без MCP: вставте таблицю в коментар до issue вручну на github.com.)

**Обговорення:** які правила дублюються між клієнтом і сервером, і чи вони однакові? Скільки місць треба змінити, щоб змінити максимальну довжину повідомлення?

## Частина 7. Аналіз впливу

```text
Ми будемо реалізовувати таку зміну:
1. Зробити телефон обов'язковим у формі контактів.
2. Додати необов'язкове поле для файлу (лише PDF, до 5 МБ).
3. Включити вкладення як посилання або завантаження в лист-сповіщення.

Проаналізуй вплив на кодову базу. Перелічи кожен файл чи область, що потребує змін,
згрупувавши за:
- компоненти UI і форми
- API-маршрути
- валідація (клієнт і сервер)
- сервіси (пошта, завантаження тощо)
- тести
- i18n / рядки перекладу
- моделі бази даних чи репозиторії (якщо є)
- конфігурація (змінні середовища, константи)
```

### Конфлікти з наявними правилами

```text
Чи суперечить запропонована зміна якимось поточним правилам у коді? Перевір:
- гілку необов'язкового телефону в validateContactData.ts
- схему Zod у ContactForm.tsx
- наявні допоміжні функції завантаження в app/services/upload/
- будь-які наявні обмеження розміру чи MIME-типу
```

**ПЕРЕВІРТЕ:** агент має помітити, чи існує `app/services/upload/`. Це можливість повторного використання, але й ризик, якщо обмеження не збігаються з новою вимогою. (Примітка: у цьому навчальному коді `upload.ts` це демо-заглушка, `streamBlob()` без аргументів падає, бо `Response.redirect` вимагає абсолютний URL. У застосунку функцію не викликають.)

## Частина 8. Критерії приймання (AC) на основі коду

AC, написані після трасування й аналізу впливу, достовірніші за написані до читання коду.

```text
На основі:
- поточної реалізації контактної форми
- констант валідації в app/constants/validation.ts
- тестів app/lib/utils/validateContactData.test.ts та
  app/shared/components/forms/contact-form/ContactForm.test.tsx
- щойно складеного аналізу впливу

Напиши повний набір критеріїв приймання для зміни з issue #<номер> у форматі:
Given [контекст], When [дія], Then [очікуваний результат]

Охопи:
- обов'язковий телефон (порожній і невалідний формат)
- вкладення (успіх, завеликий файл, неправильний MIME-тип, без файлу)
- прапорець політики конфіденційності (досі обов'язковий)
- стани кнопки відправки (вимкнена/увімкнена)
- вміст листа-сповіщення
- тексти помилок (англійською та українською)
```

### Питання до стейкхолдера

```text

перш ніж розробник зможе почати:
- конкретні числові межі (максимальний розмір, MIME-типи крім PDF?)
- поведінка локалей (якою мовою помилка валідації?)

- зберігання (куди потрапляє вкладення: диск, blob-сховище, лише лист?)
```

### Вимоги до Pull Request

PR є вашою здачею: ментор перевіряє його за критеріями дня. Щоб його можна було перевірити:

- PR відкритий із гілки `day-2` у `main` **вашого** репозиторію (не в шаблон і не в чужий); репозиторій публічний.
- Назва PR: `День 2: <коротко, що зроблено>`.
- В описі PR 2–4 речення: що ви зробили, що було складним, що лишилось незрозумілим і посилання на issue (`Related to #<номер>`).
- У PR лише файли цього дня (перевірте вкладку **Files changed**). Не має бути `.env`, `node_modules`, `.cursor/mcp.json` і токенів.
- Не закривайте PR до відгуку ментора. Після здачі злийте його в `main` вашого репозиторію (кнопка **Merge pull request**), щоб наступного дня почати з актуального `main`.

**ПЕРЕВІРТЕ перед комітом:** `git status` не показує `.cursor/mcp.json`, `.env`, `node_modules`.

**Обов'язкове:** документ `docs/contact-form-feature.md` + issue з AC, таблицею правил і питаннями. **Додатково:** коментар з аналізом впливу в issue, правило `docs-ba.mdc`, Humanizer.

## Критерії перевірки (ментору)

**Пункти 1–4 перевіряються в issue учасника** (тіло issue: AC; коментарі: таблиця правил, аналіз впливу, відкриті питання). **Пункти 5–6 перевіряються в PR.**

1. AC у форматі Given/When/Then, покривають телефон, вкладення, політику, стани кнопки, лист, помилки двома мовами (тіло issue).
2. Таблиця правил відповідає реальному коду (правила не вигадані); знайдено розбіжність клієнт/сервер (коментар «Rules table:» в issue).
3. Є відкриті питання до стейкхолдера (коментар «Open questions for the stakeholder:» в issue).
4. Видно власну правку, а не лише AI-текст (issue і документ у PR).
5. У PR є `docs/contact-form-feature.md`; PR відповідає вимогам до PR (див. вище); немає токена та службових файлів.
6. `.cursor/mcp.json` у `.gitignore`.
