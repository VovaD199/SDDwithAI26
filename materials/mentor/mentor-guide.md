# Посібник ментора: перевірка завдань курсу

> ЧЕРНЕТКА v1. Правила зарахування (поріг, терміни, повторна здача) визначені на навчальній платформі й тут **не повторюються**: орієнтуйтеся на них. Цей документ описує лише **як перевіряти** кожну здачу. Критерії зібрано з інструкцій днів 1–4.

## Як працює здача

- Учасник працює у власному репозиторії, створеному з шаблону (`SDDwithAI26-<імʼя>`), і надсилає посилання на **Pull Request** за кожен день.
- Кожен день має гілку `day-N` (день 3 також одноразова `poc/day-3`, яка не здається).
- Канал здачі: `<буде вказано в Moodle>`.

## Що перевіряється: PR і вимоги до нього

**PR перевіряється завжди**: це основна здача дня. Учасники бачать у інструкціях «Вимоги до Pull Request» і мають їх виконувати:

- PR відкритий із `day-N` у `main` власного (публічного) репозиторію учасника;
- назва `День N: <коротко>`; в описі 2–4 речення (що зроблено, що було складним, що незрозуміло); у дні 2 посилання на issue;
- у PR лише файли дня, без `.env`, `node_modules`, `.cursor/mcp.json`, токенів;
- PR не закривають до відгуку ментора; після здачі учасник зливає його у свій `main` (щоб наступного дня працювати з актуальним `main`).

**День 2 особливий:** пункти 1–4 рубрики перевіряються **в issue** (тіло з AC; коментарі «Rules table:», аналіз впливу, «Open questions for the stakeholder:»), а пункти 5–6 у PR. Тому в дні 2 учасник надсилає два посилання: на PR і на issue.

## Загальний чекліст для кожного PR (2 хв)

Перш ніж оцінювати зміст, перегляньте вкладку **Files changed**:

- [ ] У PR лише очікувані файли дня (див. таблицю нижче)
- [ ] Немає `.env`, `node_modules`, `.cursor/mcp.json`, токенів, ключів. **Якщо токен потрапив у репозиторій, повідомте учасника негайно: токен треба відкликати (навіть якщо файл видалено, він лишається в історії)**
- [ ] PR відкритий із гілки `day-N` у `main` власного репозиторію учасника (не в чужий)
- [ ] Повідомлення комітів зрозумілі

## Рубрика по днях

Для кожного критерію оцінка: **виконано / частково / не виконано** і коротка примітка учаснику.

### День 1. Старт і контекст проєкту

1. Усі кроки виконано: `AGENTS.md` і діаграма в PR.
2. `AGENTS.md` відповідає реальному проєкту: немає вигаданих сторінок, мова й конвенції (TypeScript, без default export, `uk` основна мова) збігаються з кодом.
3. Видно власну правку (не лише сирий текст AI): учасник виправив хоча б одну неточність.
4. Діаграма відображається (синтаксис Mermaid правильний) і підписана справжніми назвами папок/файлів.
5. Немає службових файлів і секретів.

**Типові помилки:** вигадані сторінки в `AGENTS.md`; діаграма не рендериться; закомічено `.env`.

### День 2. Від вимоги до коду

> Пункти 1–4 перевіряються в issue, пункти 5–6 у PR.

1. AC у форматі Given/When/Then; покривають телефон (порожній і невалідний), вкладення (успіх, завелике, не PDF, без файлу), політику, стани кнопки, лист, помилки двома мовами.
2. Таблиця правил відповідає реальному коду (є файл і джерело істини кожного правила); знайдено принаймні одну **розбіжність клієнт/сервер** (email, прапорець політики лише на клієнті).
3. Є відкриті питання до стейкхолдера (числові межі, локалі, збій завантаження, зберігання, приватність).
4. Видно власний аналіз: учасник щось виправив чи відхилив у AI-відповіді.
5. У PR є `docs/contact-form-feature.md`, PR відповідає вимогам до PR; немає токена та службових файлів.
6. `.cursor/mcp.json` у `.gitignore`; (за можливості) токен відкликано. Якщо MCP недоступний: прийнятна ручна версія (issue створено вручну, результат вставлено вручну).

**Типові помилки:** AC без «Then»; таблиця правил із вигаданими рядками; змішано аналіз впливу й AC; токен у чаті чи в коміті.

### День 3. Гіпотези та прототипи

1. Підсумок PoC має шість розділів: гіпотеза, налаштування пісочниці, зміни, докази, чекліст, наступний крок.
2. У чеклісті «доведено» лише те, що учасник **спостерігав сам** у запущеному застосунку, тобто те, що записано в `docs/poc-notes.md` (там для кожної з трьох змін є «що змінив» і «що побачив» або «не перевіряв»); «потрібен розробник» заповнено чесно (порожні рядки допустимі, якщо справді невідомо).
3. Виявлено дублювання валідації (клієнт / API / тести) або чесно позначено як нез'ясоване.
4. **Код PoC не потрапив у PR** (немає змін у `scripts/`, `app/`, `i18n/`); у PR лише два документи: підсумок і `docs/poc-notes.md`.
5. (Додатково) Аналіз макета: власні спостереження поруч з AI-аналізом; питання за категоріями.
6. Немає секретів і службових файлів.

**Типові помилки:** змішано факти й припущення («доведено» для того, чого не перевіряли); у PR потрапили зміни seed чи перекладів; підсумок для технічних, а не для стейкхолдерів.

### День 4. Структуровані специфікації

1. У специфікації є всі 8 артефактів: проблема, межі, актори й потік, правила, обмеження й залежності, припущення, відкриті питання, сигнали приймання.
2. ID (`RULE`, `OUT`, `AC`, `Q`, `ASM`) унікальні й пов'язані (правило → AC → питання).
3. Правила узгоджені з результатами дня 2 (код), мають джерело; немає вигаданих числових значень чи політики.
4. Відкриті питання мають власників; припущення позначені `ASM-##`, а не подані як факти.
5. Зріз: спростовна гіпотеза, явні OUT-пункти з причинами, два сигнали з різними порогами для PoC і продакшену, посилання щонайменше на 2 батьківські ID.
6. Видно використання запобіжників AI: мітки Grounded/Inferred/Invented й виправлені вигадки.
7. Немає секретів і службових файлів.

**Типові помилки:** довгий текст замість структури; ID без зв'язків; «Invented» без жодного виправлення; технічні рішення (стек, БД) у специфікації без запиту.

## Як давати зворотний зв'язок

- Спершу одне, що вдалося, потім не більше трьох зауважень за пріоритетом.
- Прив'язуйте зауваження до критерію рубрики (наприклад, «День 2, критерій 2»).
- Для PR використовуйте коментарі на GitHub; підсумок надсилайте у визначений канал.
- Вимоги до термінів відповіді та статусів зарахування беріть з правил на навчальній платформі.

## Допомога учасникам (типові проблеми)

| Проблема | Підказка |
|---|---|
| Не встановлюється Node/Git | Інструкція «Встановлення» (`materials/setup/`); запасні шляхи: Download ZIP, Codespaces (якщо дозволено) |
| `npm install` падає | Перевірити `node -v` (22+), мережу без VPN |
| Порт 3000 зайнятий | Використати адресу, яку показує термінал |
| MCP не підключається | Перевірити шлях `.cursor/mcp.json`, пробіли в токені, термін токена; запасний шлях без MCP |
| Нечитабельна діаграма Mermaid | Перевірити на mermaid.live |
| Заплутався з гілками у дні 3 | Скопіювати документ поза проєкт, `git checkout main`, створити `day-3`, покласти документ |
| Закомітив токен | Токен відкликати негайно, ключ вважати скомпрометованим |
